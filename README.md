# Terminal Composer

Linux-терминал с многострочным ChatGPT-подобным полем ввода вместо однострочного
shell prompt. Обычный terminal emulator (xterm.js + PTY) плюс composer, который
одинаково работает и с обычным shell, и с любым CLI-агентом (Claude Code, Codex,
Aider, …).

## Запуск в dev-режиме

Инструкция рассчитана на человека без опыта в Rust. Проверено на Ubuntu 24.04.

### 1. Системные библиотеки

Tauri рендерит окно через WebKitGTK, поэтому нужны dev-пакеты системных
библиотек:

```bash
sudo apt install -y \
  pkg-config \
  libwebkit2gtk-4.1-dev \
  libsoup-3.0-dev \
  librsvg2-dev \
  libxdo-dev \
  libayatana-appindicator3-dev \
  libdbus-1-dev
```

### 2. Rust

Если `rustc --version` ничего не выводит:

```bash
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source "$HOME/.cargo/env"
```

Отдельно ставить `tauri-cli` не нужно — он подключён как npm-зависимость проекта.

### 3. Node.js

Нужен Node 20+ (`node -v`).

### 4. Запуск

```bash
npm install
npm run tauri dev
```

Первая сборка Rust занимает несколько минут, последующие — секунды.

Полезные команды:

| Команда | Что делает |
|---|---|
| `npm run tauri dev` | запустить приложение |
| `npm test` | юнит-тесты фронтенда (vitest) |
| `npm run typecheck` | проверка типов TypeScript |
| `cd src-tauri && cargo test` | юнит-тесты Rust |

## Клавиатура

| Клавиши | Действие |
|---|---|
| `Enter` | отправить содержимое composer в терминал |
| `Shift+Enter` | новая строка в composer |
| `↑` / `↓` | предыдущие команды и сообщения (когда каретка на первой / последней строке) |
| `→` / `End` | принять продолжение, подсказанное серым |
| `Esc` сразу после отправки | вернуть текст в composer и прервать target |
| `Esc` | свернуть composer, уйти в терминал |
| `Ctrl+Shift+↑` / `Ctrl+Shift+↓` | открыть composer / убрать его и уйти в терминал |
| `Ctrl+Shift+P` | закрепить composer: клавиатура остаётся в нём |
| `Ctrl+F` | поиск по выводу активного терминала (`↑` / `↓` или `Enter` — по совпадениям, `Esc` — закрыть) |
| `Ctrl+Z` / `Ctrl+Shift+Z` | undo / redo в composer |
| `Ctrl+Shift+T` / `Ctrl+Shift+W` | новый терминал / закрыть текущий |
| `Ctrl+Tab` / `Ctrl+Shift+Tab` | следующая / предыдущая вкладка |
| `Alt+1` … `Alt+9` | вкладка по номеру |
| `Ctrl+Shift+C` / `Ctrl+Shift+V` | копировать выделенное в терминале / вставить в терминал |
| `Ctrl++` / `Ctrl+−` / `Ctrl+0` | масштаб терминала: крупнее, мельче, по умолчанию |
| `Ctrl+C` | с выделением — копировать; без выделения — сбросить черновик и прервать target |

Composer растёт по мере набора текста и упирается в `max-height` редактора
(40% высоты окна), дальше начинает скроллиться внутри себя.

Режим ввода всегда один: активна либо консоль, либо composer. Когда активна
консоль, composer уезжает вниз и остаётся выглядывать полоской — клик по ней
возвращает его обратно.

### Ключевое архитектурное правило

Composer никогда не обращается к терминалу напрямую:

```
Composer → Message → Adapter → Target (shell / Claude Code / Codex / …)
```

Composer формирует `Message` и не знает, кто на другом конце. `Adapter`
сериализует `Message` в то, что ожидает конкретный target. Поддержка нового
CLI-агента = новый файл в `src/message/adapters/`, без изменений в composer.

### Границы frontend / Rust

| | Отвечает за |
|---|---|
| Frontend | UI, composer, клавиатура, состояние редактора, attachments, layout |
| Rust | PTY, процессы, shell, файловая система, нативные события |

UI-логики в Rust нет; PTY- и процессной логики в React-коде нет.

## Отложено

Осознанно не сделано, решения приняты по ходу и записаны здесь, чтобы не
жить в переписке:

- **Поиск по паттернам.** Строка `Ctrl+F` ищет подстроку. Search-addon xterm
  умеет `regex`, `caseSensitive` и `wholeWord` — это те же опции плюс
  переключатели рядом с полем, новой машинерии не потребуется
  (`SEARCH_OPTIONS` в `src/terminal/TerminalInstance.ts`).
- **Автодополнение путей в composer.** Дополнение путей от ФС в реальном cwd
  шелла (его можно читать из `/proc/<pid>/cwd`) закрывает главный сценарий и
  стоит примерно полсреза. Полные zsh-completions через скрытый `zsh/zpty` —
  отдельная подсистема и прямой non-goal раздела 2 ТЗ.
- **Глубокая интеграция с CLI-агентом.** При создании вкладки спрашивать, что
  запускать — shell или агента; запоминать команду запуска, называть вкладку по
  первому промпту, а при следующем открытии предлагать вернуться к прошлой
  сессии. При осознанном закрытии вкладки её запись из кеша удалять.

  Как это ложится на текущую архитектуру: вкладка получает id адаптера, и
  `Adapter` подбирается по нему. Слой для этого уже есть — composer по-прежнему
  не должен знать, кто на другом конце, иначе разрушается принцип раздела 3 ТЗ.

  Чего сделать нельзя, и это важно не обещать: **контекст диалога агента нам не
  принадлежит.** Он живёт в хранилище самого агента, снаружи его не собрать и не
  восстановить. Максимум с нашей стороны — запомнить команду и каталог и
  перезапустить агента его же средствами возобновления (у Claude Code это
  `--continue` / `--resume`). То есть «восстановление сессии» — это перезапуск
  агента с просьбой продолжить, а не воскрешение процесса.

- **Обновление и откат версий в настройках.** Список версий: свежие выше
  зелёным, старые ниже красным, с возможностью и обновиться, и откатиться.

  Оговорка по объёму: это в первую очередь не UI, а дистрибуция, которую ТЗ
  выводит за рамки (раздел 2). Нужны собранные подписанные пакеты, канал
  обновлений и эндпоинт со списком версий. У Tauri есть `tauri-plugin-updater`,
  но он умеет только двигаться вперёд — откат на произвольную старую версию
  придётся строить самим поверх собственного списка релизов. Пока нет упаковки,
  делать тут нечего.

- **Стартовое имя вкладки от терминала.** Сейчас это «Терминал N» с
  переименованием по двойному клику. Осмысленное имя из запущенной программы
  или каталога упирается в вопрос, что показывать, когда программа сменилась.

## Заметки по реализации

**Bracketed paste и отправка.** Многострочный текст отправляется как paste
(`ESC[200~ … ESC[201~`), иначе обычный shell выполнил бы его построчно.
Поддерживает ли это программа на другом конце, определяется по режимам,
которые она включила (`Terminal.modes.bracketedPasteMode` в xterm.js), и
передаётся адаптеру как `TargetCapabilities`. Если bracketed paste выключен,
текст уходит как есть — мы не подсовываем target escape-последовательности,
которых он не просил.

**Язык интерфейса.** Английский — база: его словарь полный, и именно его ключи
образуют тип, поэтому недостающий русский перевод — ошибка компиляции, а не
пустая подпись. Системный язык только предлагается при первом запуске.

**Настройки — такая же вкладка, как терминал.** Не диалог и не отдельный режим:
их можно открыть сколько угодно раз, они переставляются и закрываются наравне с
терминалами — крестиком или средней кнопкой мыши. Composer при этом не
размонтируется, а прячется, поэтому возврат на терминал ничего не пересоздаёт.

**Сохранение между запусками.** Два документа рядом с конфигом приложения:
`settings.json` и `workspace.json`. Rust умеет только читать и писать документ
по имени — форма данных целиком принадлежит фронтенду, чтобы модель продукта не
протекала в нативный слой. Запись идёт через временный файл с переименованием,
поэтому падение посреди записи не оставит половину документа. Восстанавливаются
терминалы, их порядок, имена, рабочие каталоги и черновики composer;
запущенные в них программы — нет, они умерли вместе с прошлым процессом.

**Перестановка вкладок** сделана на pointer-событиях, а не на HTML5 drag & drop:
нативный оконный drag-drop включён ради вложений, а HTML5-перетаскивание внутри
страницы на GTK превращается в системное — эти два механизма дрались бы за одно
и то же (риск №5 из ТЗ).

**Продолжение серой тенью.** Начали набирать то, что уже запускали — остаток
строки появляется после каретки серым, как в шелле. `→` или `End` принимает его.
Ничего не вставляется, пока не приняли: текст остаётся ровно тем, что набрали.
Предлагается только в конце однострочного поля — с кареткой посреди сообщения
это было бы догадкой про текст, который и так там есть.

**История помнит и то, что набрано в терминале.** Шелл сообщает каждую команду
вместе с меткой о её запуске, поэтому `↑` в composer достаёт и отправленное из
поля, и набранное прямо в терминале — это один список, а не два. Команда,
отправленная из composer, приходит дважды: от нас и от шелла, который её
выполнил, — повтор подряд отбрасывается. Внутри `docker exec` или `ssh` команд
не видно по той же причине, что и состояния: там другой шелл.

**Черновик у каждой сессии.** Composer один, но его содержимое и история
принадлежат активному терминалу: при переключении текущий документ сохраняется
за уходящей сессией, а на его место встаёт документ входящей. Состояния
закрытых сессий выбрасываются.

**Переключение вкладок.** Все вкладки остаются смонтированными, неактивные
только скрыты `display: none` — именно это сохраняет scrollback, позицию
прокрутки и запущенные программы при переключении. Скрытый терминал не имеет
размера, поэтому при возврате его заново подгоняют под контейнер. Сами объекты
терминалов живут не в сторе, а в отдельной карте: они владеют DOM и PTY, то
есть это ресурсы, а не состояние. Composer один на всё окно и всегда пишет в
активную сессию — адаптер и `Message` от количества сессий не зависят.

**Drag & drop.** Файлы принимаются нативным оконным событием Tauri
(`onDragDropEvent`), а не HTML5 DnD: внутри webview HTML5 реальных путей не
отдаёт — тот же корень, что у вставки из буфера. Событие приходит на всё окно и
сообщает курсор в физических пикселях, поэтому принадлежность броска composer
определяется сравнением с его прямоугольником (с поправкой на
`devicePixelRatio`). Начало перетаскивания разворачивает composer, чтобы
целиться не в полоску 44 px. Дальше пути уходят в ту же команду `file_info` и
превращаются в те же `Attachment`, что и из буфера обмена.

**Раскладка и Ctrl-шорткаты.** ProseMirror сопоставляет `Mod-c` с `event.key`,
то есть с тем, что выдаёт раскладка: при русской раскладке Ctrl+C приходит как
`«с»` и не совпадает. Запасной путь ProseMirror через `event.keyCode` не
спасает — WebKitGTK не отдаёт там физическую клавишу для нелатинских
раскладок. Поэтому Ctrl-шорткаты composer разбираются по `event.code`
(физическая клавиша), а в keymap остались только клавиши без символа — Enter,
Escape, стрелки.

**Дополнение.** Два источника, и выбирает между ними положение каретки. Первое
слово строки — это команда, и что за команды бывают, **сообщает сам шелл**: наш
файл интеграции на первом же приглашении выгружает алиасы, функции и всё из
`$PATH`. Алиасы вроде `gst` знает только он — никакой сторонний список команд их
не содержит. Всё остальное — путь, от живого `cwd` шелла, поэтому `src/App`
дополняется тем же, чем дополнился бы в терминале.

После команды предлагается то, что принимает она сама — подкоманды и флаги.
Описания команд (открытые спецификации Fig, MIT) **лежат в репозитории** и едут
внутри сборки: пакет публикует их за `exports` без глубоких импортов, а качать
что-либо на ходу терминал не должен. Везём отобранные 40 команд, 1,6 МБ, каждая
подгружается в момент, когда её набрали. Полная коллекция — 73 МБ и 1541 файл,
почти всё про инструменты, которых здесь никто не запускает. Динамические
значения (ветки для `git checkout`) не вычисляются: их дают запуском команд, а
запускать что-то ради выпадающего списка — отдельное решение.

Сам собой список появляется, **пока composer это командная строка**, и для
всего, что уже похоже на путь. В сообщении он ждёт, когда попросят: перечень
каталога не должен лезть поверх текста, который вы пишете агенту. `Tab` просит
всегда. Каталог подставляется со слэшем и список открывается снова — путь
проходится шаг за шагом.

**Ссылки на файлы.** Имена файлов в выводе терминала кликабельны, и решает это
файловая система, а не форма слова: строка разбирается на кандидатов, все они
проверяются **одним** запросом, и ссылкой становится только то, что существует
на самом деле. Относительные пути разрешаются от живого `cwd` шелла, поэтому
`src/App.tsx` значит там же, что и в терминале. Иначе подчёркивалось бы каждое
слово с точкой.

Файл открывается **новой вкладкой в ряду под шапкой**: первая вкладка — сам
терминал, дальше открытые из него файлы, как в редакторе кода. Открытый файл
сразу в фокусе, закрывается крестиком или средним кликом. Ряд появляется только
когда файл открыт — одна вкладка над терминалом была бы подписью, а не выбором.
Набор принадлежит вкладке терминала, поэтому переключение вкладок его не теряет. Markdown рисуется, остальное показывается как текст,
картинки как картинки. Только просмотр: редактирования нет, оно уводило бы в
IDE-функциональность из non-goals ТЗ. Сырой HTML в markdown не рендерится —
открываем то, на что показал терминал, и доверия к этому нет.

**Кто владеет клавиатурой.** Определить «программа сейчас ждёт от тебя ответа»
нельзя: в протоколе терминала такого понятия нет, и любая попытка вывести это из
вывода — догадка, которая ломается на следующей программе. Поэтому мы не гадаем,
а спрашиваем шелл.

Шелл печатает метки **OSC 133** — существующий стандарт, его понимают WezTerm,
kitty, VS Code: `A` и `B` — приглашение готово, жду ввод; `C` — команда пошла;
`D;<код>` — команда завершилась. Отсюда правило целиком:

- шелл ждёт команду → клавиатура у composer;
- что-то выполняется → клавиатура у терминала, **чем бы оно ни было**: `htop`,
  `claude`, `apt` со своим `[Y/n]`, приглашение пароля;
- завершилось → обратно к composer.

Ни одного условия про конкретные программы, ни одной эвристики.

**Как это ставится.** Шелл запускается с `ZDOTDIR`, указывающим на наш
каталог, — и там подменён **только `.zshenv`**. Он подключает пользовательский
`.zshenv`, сразу возвращает `ZDOTDIR` обратно и уходит с дороги: `.zprofile`,
`.zshrc` и `.zlogin` zsh читает у пользователя ровно так, как читал бы без нас.
Возврат должен произойти до пользовательского конфига, иначе `compinit`
пересобирает кэш дополнений во временный каталог при каждом запуске. Приглашение не трогаем — только хуки `precmd` и `preexec`, иначе
подрались бы с оболочками вроде p10k. Метки принимает `parser.registerOscHandler`
у xterm, поток в Rust не разбирается.

**Клавиатура всегда у кого-то.** Промежуточного состояния «ни терминал, ни
composer» быть не должно: нажали вкладку или кнопку — и следующая клавиша ушла
бы в никуда. Поэтому элементы обвязки помечены как не забирающие фокус
(`keepFocus`), а на случай клика мимо них есть страховка: если фокус оказался на
самой странице, активная панель забирает его обратно. Текстовые поля — поиск,
переименование, настройки — исключение: им клавиатура и нужна.

**Один уровень вглубь.** Интеграция говорит за тот шелл, в котором живёт. Внутри
`docker exec`, `ssh`, `tmux` или вложенного шелла работает **другой** шелл, и
нашего файла там нет: внешний видит одну выполняющуюся команду и больше ничего,
поэтому «внутреннее приглашение ждёт» не скажет никто. Гадать тут нечем, поэтому
есть явный рычаг — **закрепить composer** (`Ctrl+Shift+P` или кнопка в углу
поля): пока закреплён, автоматика к фокусу не прикасается, а ручное переключение
работает как обычно.

**Когда интеграции нет** — другой шелл, выключено в настройках, не подхватилось —
шелл ничего не сообщает, и приложение тоже ничего не выдумывает: клавиатура
остаётся там, куда её поставил пользователь, а composer открывается руками.
Пока поддержан только zsh; у fish и bash есть свои способы внедрения, и они
проще зшевского.

**Клавиши терминала.** xterm.js выводит и управляющие символы, и печатаемый
ввод из `event.keyCode`: `Ctrl`+буква из диапазона 65..90, а символ отправляет
только при `keyCode >= 48`. WebKitGTK не кладёт туда физическую клавишу для
нелатинских раскладок — при русской раскладке `Ctrl+C` не превращался в `0x03`,
а буквы либо не проходили условие, либо приходили дважды: из обработчика клавиш
и из скрытой textarea. Поэтому эти два случая разбираются по `event.code` и
`event.key` и возвращаются в терминал через его же `input()`, чтобы порядок,
прокрутка и очередь записи работали как для остальных клавиш. Всё остальное —
стрелки, функциональные клавиши, IME — оставлено xterm.

**Порядок ввода.** Нажатия клавиш не отправляются в PTY по одному `invoke` на
клавишу: каждый вызов — независимое IPC-сообщение, и Tauri вправе обрабатывать
их параллельно, из-за чего при быстром наборе байты доезжали до shell вперемешку.
`TerminalInstance` держит **одну** запись в полёте и склеивает всё, что успело
накопиться за ней, — это гарантирует порядок и заодно сокращает число round-trip.

**Отмена отправки.** Un-send невозможен: байты уже в PTY. Поэтому `Esc` в
течение 4 секунд после отправки возвращает текст в composer и просит target
прерваться — через `Adapter.abort()`, потому что «как прервать» это знание о
target. Для shell-адаптера это `ESC`, а следом `Ctrl+U`: агент, который по
прерыванию возвращает промпт в собственное поле ввода, иначе оставил бы текст
сразу в двух местах. `Ctrl+C` намеренно не шлём — случайный `Esc` не должен
убивать процесс.

Завершающий `CR` уходит **отдельной записью с паузой** после вставки. TUI на
Ink (Claude Code в их числе) считают ввод, пришедший вплотную за вставкой,
продолжением этой же вставки, и `CR` в том же куске попадает к ним в поле
ввода переносом строки вместо отправки. Поэтому `Adapter.serialize` возвращает
последовательность `PtyWrite`, а не одну строку: тайминг — часть контракта с
target, и знание о нём живёт в адаптере.

**Батчинг вывода PTY.** Вывод не пересылается во frontend по чанку на событие:
поток-читатель складывает данные в канал, второй поток склеивает их и отдаёт
не чаще, чем раз в 8 мс (или сразу при накоплении 64 КБ). Многобайтовые
UTF-8 символы, разорванные между чтениями, склеиваются, а не превращаются в
кракозябры.

**Завершение процессов.** При закрытии сессии убивается не только shell:
интерактивная задача (например `claude`) живёт в собственной process group,
поэтому мы находим все процессы PTY-сессии через `/proc` и шлём им `SIGHUP`,
а через 150 мс — `SIGKILL`.

**Буфер обмена и сессия рабочего стола.** Вставка файлов и картинок идёт
мимо webview: `clipboardData` не отдаёт реальные пути. Rust спрашивает у
системного буфера, что тот предлагает, в таком порядке: `text/uri-list` и
`x-special/gnome-copied-files` (файлы), затем `image/png`, `image/webp`,
`image/jpeg`, `image/gif`. Обычный текст не трогаем — его webview вставляет
сам. У картинки из буфера нет пути, поэтому байты пишутся во временный файл в
`$XDG_RUNTIME_DIR/terminal-composer/` (чистится при старте) — у вложения всегда
есть путь, это контракт с target.

Backend выбирается не по типу сессии, а перебором. `wl-clipboard-rs` требует
Wayland-протокол data-control, который есть у wlroots-композиторов, но **не** у
GNOME/Mutter из Ubuntu 24.04 (GNOME Shell 46). Под GNOME работает X11-путь:
XWayland запущен, а сессия связывает оба буфера. Поэтому сначала пробуем
Wayland, при неудаче — X11.

Проверено на Ubuntu 24.04, **Wayland-сессия GNOME Shell 46**: и картинка, и
файл с пробелом в имени доезжают через X11-ветку. На чистом wlroots-сеансе
должна сработать Wayland-ветка, но там не тестировалось.
